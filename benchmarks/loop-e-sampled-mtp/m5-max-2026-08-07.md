## Claim under test

Sampled MTP spec decode — `BUTTER_QWEN_MTP_SPEC=1` + `BUTTER_QWEN_MTP_STATE_REWIND=1` +
`BUTTER_QWEN_MTP_BATCHED_LOCKSTEP=1` + `BUTTER_QWEN_MTP_GAMMA=3`, temperature 0.6,
match-accept scheme — is **lossless**: every emitted token is a true draw from the
same filtered distribution the no-spec sampler draws from.

Prior evidence: 2 seeded digest matches (existence proof, n=2, not a statistical
gate). This run is the RST-AI Loop E gate that existence proof was missing.

### Step 1 — FIRST-TOKEN distribution

| Stat | Value |
|---|---|
| Test | `scipy.stats.chi2_contingency` (Pearson chi-square, RxC contingency) |
| Categories | 5 (4 recurring ids + pooled "other" tail) |
| df | 3 |
| statistic | 0.0000 |
| p-value | 1.0 |

**FINDING (confound):** 30/30 seed-paired runs produced an *identical*
`first_token` across arms. This is structurally expected, not surprising: per
`Generate.swift`, the very first generated token is emitted by the chunked-prefill's
own categorical sampler **before** the spec-decode loop is even entered — for a
fixed seed it depends only on arm-independent prefill logits + RNG state at that
exact point, regardless of `BUTTER_QWEN_MTP_SPEC`. This stat mainly verifies the
prefill-sampler path is arm-invariant; it is weak evidence about the MTP
accept/reject scheme specifically. See the 1b diagnostic below for the targeted
check.

### Step 2 — LENGTH (tokens-to-stop) distribution

| Stat | Value |
|---|---|
| Test | `scipy.stats.mannwhitneyu` (two-sided) |
| statistic (U) | 450.0 |
| p-value | 1.0 |

**FINDING (degenerate/testability gap):** every run in both arms (60/60) hit the
`--max-tokens 64` cap; EOS never fired for this prompt at this length. Both arms
have **zero variance**, so U = n1\*n2/2 and p = 1 **by construction**, not because
the distributions genuinely agree. This stat currently carries **no statistical
power** under this prompt/cap configuration. To make it informative, a future run
needs either a prompt that lets EOS fire before the cap, or a shorter
`--max-tokens`.

### Step 1b — SECOND-TOKEN distribution (supplementary diagnostic, added mid-harness, not part of the alpha=0.01 gate)

The second token is the first position genuinely reachable by the MTP
accept/reject path (`gamma=3` batched-lockstep draft/verify), so it is a more
targeted check of the actual claim under test than the first token.

| Stat | Value |
|---|---|
| Test | `scipy.stats.chi2_contingency` |
| Categories | 5 |
| df | 4 |
| statistic | 4.0000 |
| p-value | 0.406 |

Unlike the first-token stat, this one shows **genuine per-seed divergence**
between arms — e.g. seed `20260826`: spec-off `second_token=48611`, spec-on
`second_token=3753` — confirming the accept/reject path really is exercised and
really does draw differently run-to-run. The aggregate distributions are still
statistically indistinguishable (p=0.406, nowhere near alpha=0.01), consistent
with (not proof of) the lossless claim.

## Testability gaps found (for the record)

1. **First-token confound.** Comparing `first_token` across arms with a shared
   seed is close to tautological — that draw happens before spec decode engages.
   Fixed in-session by adding a `second_token` diagnostic (harness now records
   both). A cleaner long-term fix: have the harness compare per-position token
   distributions from position 1 onward (would require the CLI to expose more of
   the id stream than just a flat digest+first_token, which it now does via
   `--print-token-ids` — the harness only needed to read one more list index).
2. **Length-stat degeneracy.** `"The history of computing is"` at
   `--max-tokens 64` never lets EOS fire in either arm. The Mann-Whitney length
   test is currently vacuous. Needs a prompt/cap pairing where EOS is reachable
   (e.g. a short factual Q&A prompt, or `--max-tokens 16-24`) to give this stat
   real power. Left as-is for this run per the task's fixed sampling config
   (prompt/max-tokens were specified, not discovered); flagging for the next
   run rather than silently swapping the fixed config out from under the gate.
3. **`--seed` CLI support:** confirmed present (`GenerateCommand.swift:104-105`,
   wired through `GenerationParameters.seed`) — no testability gap here, the
   harness uses it directly. No env-var fallback was needed.
4. **Token-id visibility:** the `butter generate` CLI had no way to emit raw
   token ids before this session; added `--print-token-ids` (additive-only
   flag, see the commit touching `Sources/ButterCLI/GenerateCommand.swift`)
   specifically so this harness could compute first/second-token and a
   full-sequence digest without scraping decoded text.

## Release gate

Per the harness header comment (`scripts/loop_e_sampled_mtp.py`): if this run
PASSes (it did), **this harness becomes the required release gate for any future
change to the sampled-MTP accept/match scheme** — `Qwen3x SpecDecode.generateSampledMTP`
and anything touching `Sampling.buildFilteredWeights` along that path. Re-run
before merging such a change; a regression here should block the merge the same
as a red CI gate. Given finding #2 above, a future maintainer extending this gate
should also swap in a prompt/max-tokens pairing that lets EOS fire, so the length
stat stops being vacuous.
